# Спринт 2: основа Firewall

[English version](sprint-2.md)

## Мета та обсяг

Доповнити топологію спринту 1 відтворюваною ізоляцією Guest → Corporate та IoT → Corporate. Це основа Firewall для R-02, R-07 та D-01 із наданого шаблону Sprint 2. Початкові практичні докази наведені нижче; цей опис не є завершеним Sprint 2 Record або рішенням про Implementation Freeze.

## Реалізація

- `gateway/Dockerfile` встановлює nftables під час збирання образу.
- `gateway/nftables.conf` керує лише таблицею `inet lab_filter`. Повторне завантаження атомарно замінює її правила, не видаляючи інші таблиці, зокрема майбутній NAT.
- Docker Compose вмикає пересилання IPv4. Entrypoint завантажує правила до успішного healthcheck; помилка конфігурації зупиняє шлюз. Під час запуску Compose інші сервіси очікують його готовності. Цей порядок не гарантує безперервного блокування під час пересоздання шлюзу з уже запущеними клієнтами; перед продовженням тестів перевірте політику повторно.
- Пакети з Guest (`172.28.10.0/24`) та IoT (`172.28.30.0/24`) до Corporate (`172.28.20.0/24`) блокуються до перевірки established/related. Кожне обмеження має іменований лічильник.
- Інший established/related трафік дозволений; решта транзитного трафіку блокується. Нових міжзонних або інтернет-з'єднань ця основа не дозволяє. Локальні input/output шлюзу не змінені: клієнти можуть перевірити шлюз через ping, а шлюз — звернутися до Nginx.

Правила діють усередині контейнера шлюзу, а не на хості. Це стенд із довіреними клієнтами: клієнти мають `NET_ADMIN` для налаштування маршрутів. Модель не захищає від навмисної зміни маршрутів або підміни IP учасником.

## Команди перевірки

```bash
docker compose config --quiet
docker compose up -d --build --wait
docker compose ps
sh scripts/check-isolation.sh
docker compose restart gateway
sh scripts/check-isolation.sh
docker compose up -d --force-recreate --wait
sh scripts/check-isolation.sh
```

Скрипт завершується помилкою, якщо сайт або шлях до шлюзу не працює, клієнтський HTTP-запит успішний чи відповідний лічильник Firewall не збільшується. Сам таймаут не вважається доказом ізоляції. Під час перевірки не запускайте інший клієнтський трафік, щоб пов'язати лічильники саме з тестовими запитами.

Для скріншотів термінала можна виконати команди вручну:

```bash
docker compose exec gateway nft list table inet lab_filter
docker compose exec internal-site wget -T 3 -t 1 -qO- http://172.28.20.10
docker compose exec gateway wget -T 3 -t 1 -qO- http://172.28.20.10
docker compose exec guest-client ping -c 1 172.28.10.254
docker compose exec iot-client ping -c 1 172.28.30.254
docker compose exec guest-client wget -T 3 -t 1 -qO- http://172.28.20.10
docker compose exec iot-client wget -T 3 -t 1 -qO- http://172.28.20.10
docker compose exec gateway nft list table inet lab_filter
```

HTTP-запити з обох клієнтів мають завершитися помилкою; запити із сайту та шлюзу — успішно. Порівняйте лічильники Firewall до та після клієнтських запитів.

## Завдання учасникам

Детальні інструкції для передачі виконавцям або іі: [завдання для завершення sprint-2](sprint-2-handoff-ua.md).

1. **Інтернет для Guest:** налаштувати маршрутизацію, явний дозвіл виходу Guest в інтернет, зворотний трафік та NAT на шлюзі. Зберегти блокування Corporate і Default Deny. Використати окрему NAT-таблицю, щоб перезавантаження `lab_filter` її не видаляло. Перевірити зовнішній запит саме з `guest-client`; запит зі шлюзу не доводить доступ Guest. Під час фіксації маршруту врахувати DNS та вбудований resolver Docker.
2. **Перевірки та докази:** виконати контрольні запити й перевірки ізоляції, повторити після перезапуску та пересоздання контейнерів. Після роботи першого учасника перевірити також інтернет Guest. Зберегти фактичні результати й скріншоти в `evidence/sprint-2/`: команда, очікування, фактичний результат, PASS/FAIL, шлях до доказу. Для помилок описати кроки відтворення.

Реалізація Auth Portal та автоматичні рольові дозволи не входять до цієї основи. Опис порталу та матрицю ролей потрібно завершити окремо; сам Firewall не є підставою позначати вимоги автентифікації READY.

## Стан перевірки

Автор проєкту надав вивід термінала 26 жовтня 2026 року. Образ шлюзу успішно зібрано, запуск Compose завершено зі здоровим шлюзом, а завантажена таблиця nftables містить потрібні правила. Доказ: [початковий вивід термінала](../evidence/sprint-2/initial-isolation-2026-10-26.txt).

| Перевірка | Фактичний результат | Статус |
| --- | --- | --- |
| Internal Site усередині Corporate | Повернуто вітальну сторінку Nginx. | PASS |
| Gateway → Internal Site | Повернуто вітальну сторінку Nginx. | PASS |
| Guest та IoT → власний шлюз | Кожен ping отримав 1/1 відповідь, 0% втрат. | PASS |
| Guest → Internal Site | HTTP-таймаут; guest_to_corporate packets збільшився з 0 до 3. | PASS |
| IoT → Internal Site | HTTP-таймаут; iot_to_corporate packets збільшився з 0 до 3. | PASS |

Таблиця вище зберігає результати початкового запуску автором. Новий повний запуск 26 жовтня 2026 року також підтвердив ізоляцію після перезапуску шлюзу та пересоздання всіх чотирьох контейнерів. На кожному етапі сайт і шлюзи доступні, а запити Guest/IoT блокуються зі зростанням лічильників Firewall. Див. [повні результати, середовище та логи](../evidence/sprint-2/results.md). Повторити збір можна командою `sh scripts/collect-isolation-evidence.sh`.

Налаштування та перевірка інтернету Guest залишаються завданням іншого учасника. Скріншоти термінала ще потрібно додати; збережені докази — фактичний вивід команд. Ці перевірки підтверджують ізоляцію після готовності контейнерів, а не безперервність блокування під час пересоздання. Для загальної готовності до Freeze потрібні також решта вимог та командний запис.
