# sprint-2 — завдання для завершення

цей опис можна передати іі разом із актуальним репозиторієм `huawei-lab`. перед змінами прочитай `README-ua.md`, `docker-compose.yml`, `gateway/`, `scripts/check-isolation.sh` та `sprints/sprint-2-ua.md`. виконуй лише своє завдання; не переписуй готову основу й не видаляй чужі зміни.

## що будуємо

кінцева ідея: пристрій уже підключений до гостьової мережі, користувач входить через auth-форму, портал визначає роль і просить шлюз відкрити дозволені внутрішні сервіси. вихід або завершення сесії має закривати доступ. авторизація змінює дозволи, а не переміщує пристрій до іншої docker-мережі.

у цьому спринті готуємо мережеву основу: ізоляцію, гостьовий інтернет, відтворювані перевірки та опис майбутнього порталу. реалізація форми, бекенду авторизації та автоматичних дозволів після входу зараз не доручається цим двом учасникам.

## що вже зроблено

| компонент | адреса / призначення |
| --- | --- |
| `guest-client` | `172.28.10.10`, гостьовий пристрій |
| `iot-client` | `172.28.30.10`, тестовий iot-пристрій |
| `internal-site` | `172.28.20.10:80`, nginx замість майбутньої платформи |
| `gateway` | `.254` у кожній із трьох підмереж, маршрутизація та nftables |

підмережі: guest `172.28.10.0/24`, corporate `172.28.20.0/24`, iot `172.28.30.0/24`. адреси `.1` належать docker-мостам, а `.254` — нашому шлюзу. клієнти й сайт використовують наш шлюз як default route.

таблиця `inet lab_filter` блокує guest → corporate та iot → corporate. решта нових транзитних з'єднань також блокується за default deny. є дозвіл established/related. конфігурація завантажується під час запуску шлюзу, інші сервіси очікують його healthcheck. інтернет і nat ще не налаштовані.

автор уже запустив модель: образ зібрався, сайт і шлюз доступні, обидва заборонені http-запити завершилися таймаутом, відповідні лічильники блокування зросли з 0 до 3. це початкова перевірка, а не підтвердження роботи після перезапуску. скріншоти ще потрібно зробити.

## учасник 1 — інтернет для гостя

### завдання

зроби так, щоб `guest-client` міг виконати зовнішній http/https-запит через `gateway`, зберігши обидві блокировки corporate.

1. перевір поточні маршрути в контейнерах. забезпеч робочий зовнішній маршрут шлюзу; за потреби додай йому окрему uplink-мережу в compose. не припускай, що зовнішній інтерфейс завжди має назву `eth0`.
2. додай явний дозвіл нового гостьового трафіку до зовнішньої мережі перед фінальним drop. обмеж дозвіл гостьовою підмережею та потрібним зовнішнім напрямком, збережи ізоляцію решти зон і default deny.
3. налаштуй masquerade для гостьової підмережі на зовнішньому інтерфейсі в окремій nftables nat-таблиці. завантажуй її автоматично та без дублювання правил. не використовуй `flush ruleset`, який видалить усі таблиці.
4. забезпеч роботу dns для гостьового запиту. врахуй, що вбудований dns docker може обробляти резолвінг окремо: саме розпізнавання домену не доводить проходження вебтрафіку через наш шлюз.
5. додай лічильник дозволеного гостьового вебтрафіку на шлюзі. покажи маршрут клієнта та збільшення цього лічильника під час зовнішнього запиту з `guest-client`. не вважай запит із самого `gateway` доказом інтернету гостя.
6. додай `scripts/check-internet.sh`: обмежений за часом зовнішній запит із `guest-client`, зрозумілий результат і ненульовий код завершення при помилці. задокументуй використаний тестовий ресурс; не покладайся лише на ping.
7. повторно запусти перевірку ізоляції. повтори інтернет і блокування після перезапуску та пересоздання контейнерів.

### що здати

- зміни конфігурації в репозиторії та скрипт перевірки інтернету;
- короткий опис запуску та змін у документації;
- фактичний вивід зовнішнього запиту з гостя, маршруту та лічильника шлюзу;
- підтвердження, що `sh scripts/check-isolation.sh` продовжує проходити.

не з'єднуй клієнта напряму з corporate або uplink, не перенаправляй його default route на docker-міст `.1`, не публікуй внутрішній сайт на хості для обходу шлюзу. не додавай auth portal або рольові дозволи в межах цього завдання.

## учасник 2 — перевірки та докази

### завдання

почни з перевірок уже готової ізоляції. після отримання змін учасника 1 перевір фінальну спільну версію разом з інтернетом. якщо скрипта `scripts/check-internet.sh` ще немає, познач інтернет як очікувану залежність, а не як успішну перевірку.

для фінальної версії виконай із кореня репозиторію:

```bash
docker compose config --quiet
docker compose up -d --build --wait
docker compose ps
sh scripts/check-isolation.sh
sh scripts/check-internet.sh
docker compose restart gateway
docker compose up -d --wait
sh scripts/check-isolation.sh
sh scripts/check-internet.sh
docker compose up -d --force-recreate --wait
sh scripts/check-isolation.sh
sh scripts/check-internet.sh
```

потрібно підтвердити:

- сайт працює всередині corporate та доступний зі шлюзу;
- guest та iot бачать власний шлюз;
- guest не відкриває внутрішній сайт, лічильник `guest_to_corporate` зростає;
- iot не відкриває внутрішній сайт, лічильник `iot_to_corporate` зростає;
- зовнішній вебзапит із гостя проходить через наш шлюз;
- ті самі результати отримано після перезапуску шлюзу та пересоздання контейнерів.

сам таймаут не є достатнім доказом блокування: перевір доступність сайту й лічильники. якщо docker не запущений або середовище не дозволяє виконати тест, запиши це як блокер; не вигадуй результати.

### що здати

збережи у `evidence/sprint-2/` фактичні логи й скріншоти термінала та створи `evidence/sprint-2/results.md` із таблицею:

| перевірка / етап запуску | команда | очікуваний результат | фактичний результат | статус | файл доказу |
| --- | --- | --- | --- | --- | --- |

для кожної помилки вкажи кроки відтворення, вплив і кому її передати. запиши дату, операційну систему, версії docker/compose та перевірений git commit. якщо є незакомічені зміни, явно зазнач це: один commit не описує таку конфігурацію повністю. спочатку збережи докази, потім онови статуси в документації спринту. не змінюй політику firewall лише для отримання успішного тесту.

## що залишається координатору

- остаточний опис auth portal: go `net/http`, html/css/js, sqlite, перевірка пароля за хешем, роль з облікового запису, сесія та майбутній зв'язок зі шлюзом;
- матриця ролей student / teacher / admin та майбутніх внутрішніх ресурсів; ці ресурси поки не реалізовані тестовим nginx;
- sprint 2 record для лабораторної 13 на основі фактичних результатів;
- freeze record для лабораторної 14: конкретна версія, smoke check, готовність вимог, відомі проблеми й тести для наступного заняття;
- кожен учасник самостійно заповнює свій рядок contribution log #4.

робоча ізоляція не означає готовність авторизації. відсутній портал потрібно залишити як відому недоробку; його програмна реалізація не є критерієм приймання цих двох завдань.
