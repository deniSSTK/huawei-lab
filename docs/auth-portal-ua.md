# локальний auth portal і матриця доступу

цей документ фіксує обраний у sprint 2 спосіб реалізації авторизації для навчального poc. портал, облікові записи та рольові дозволи поки не реалізовані програмно. зараз працюють гостьовий вебдоступ через gateway і блокування guest/iot → corporate.

## компоненти та спосіб входу

один майбутній контейнер `portal` обслуговуватиме html/css/js та api через go `net/http`. sqlite зберігатиме тестових користувачів і сесії. портал буде доступний із guest до входу; маршрути до внутрішніх ресурсів і надалі проходитимуть через окремий gateway із nftables.

користувач відкриває `/login`, вводить логін і пароль або натискає «продовжити як гість». backend перевіряє пароль за збереженим хешем із сіллю та отримує роль із запису користувача в sqlite. роль не надсилається як довірене значення з браузера і не обирається користувачем. неправильний пароль не створює ані сесію, ані мережевий дозвіл.

тестові ідентичності для майбутнього початкового наповнення бази:

| логін | роль | стан |
| --- | --- | --- |
| `student.test` | student | визначено; ще не створено |
| `teacher.test` | teacher | визначено; ще не створено |
| `admin.test` | admin | визначено; ще не створено |

паролі задаються локально під час майбутнього наповнення бази й не зберігаються відкритим текстом у репозиторії. для перевірки паролів використовується спеціалізована бібліотека хешування, а не звичайний sha256. конкретну бібліотеку й параметри потрібно зафіксувати разом із кодом авторизації.

## сесія та надання доступу

1. після успішного входу backend створює випадковий непрогнозований токен сесії. у браузері він зберігається в cookie з httponly і samesite; у базі — його хеш, користувач, ip клієнта та час завершення сесії. для https додається secure.
2. ip визначається з реального з'єднання. довільні заголовки на кшталт `x-forwarded-for` від клієнта не приймаються за довірені. у стенді один ip відповідає одному пристрою та одній активній ідентичності.
3. backend через окремий закритий інтерфейс керування просить gateway надати цьому ip лише дозволи з матриці нижче. керувальний інтерфейс не доступний із guest та iot; запити керування автентифікуються. протокол і адреса цього інтерфейсу фіксуються на етапі реалізації.
4. gateway застосовує дозволи через nftables-набори з часом дії. портал підтверджує надання мережевого доступу лише після успішного застосування правил. якщо gateway недоступний, доступ не відкривається.
5. logout або завершення сесії видаляє дозволи. таймаут на gateway закриває доступ незалежно від того, чи працює портал. повторний вхід іншою роллю спочатку скасовує попередній дозвіл пристрою.

вхід не переносить пристрій до corporate: пристрій залишається в guest, змінюються лише дозволи gateway.

## цільова матриця ролей

ресурси нижче логічні й ще не розгорнуті. поточний nginx `172.28.20.10:80` є лише спільним тестовим сайтом для перевірки ізоляції.

| роль | зовнішній вебдоступ | кабінет студента та навчальні матеріали | сервіс викладача | адміністративна сторінка |
| --- | --- | --- | --- | --- |
| guest, без входу | дозволено tcp 80/443 | заборонено | заборонено | заборонено |
| student | дозволено | дозволено | заборонено | заборонено |
| teacher | дозволено | дозволено | дозволено | заборонено |
| admin | дозволено | дозволено | дозволено | дозволено |

admin означає доступ до всіх визначених тестових сервісів, а не необмежений доступ до будь-яких мереж або керування firewall. ізоляція iot → corporate не залежить від ролі користувача.

щоб різні ролі можна було розрізняти мережевими правилами, ресурси слід надати через окремі адреси або порти. firewall не може розділити шляхи `/student`, `/teacher` та `/admin` одного http-сайту лише за ip і портом; перевірку таких шляхів додатково виконує сама платформа.

під час реалізації рольові дозволи для конкретних адрес і портів потрібно розмістити перед загальним drop guest → corporate. за відсутності чинного дозволу блокування має спрацьовувати також для встановленого раніше з'єднання, перед established/related. правило iot → corporate залишається безумовним. остаточні ip/порти рольових сервісів і керувального інтерфейсу є завданням наступного етапу, а не приховано готовою конфігурацією цього спринту.

## майбутні перевірки авторизації

| сценарій | очікування | поточний стан |
| --- | --- | --- |
| guest відкриває форму до входу | форма доступна | blocked до реалізації portal |
| неправильний пароль | відмова, сесія й дозвіл не створені | blocked |
| вхід кожним тестовим користувачем | показано роль із бази | blocked |
| прямий запит до внутрішнього ресурсу після входу | доступ лише за матрицею | blocked |
| інший неавторизований пристрій | доступ залишається закритим | blocked |
| logout або завершення сесії | закрито нові та попередні з'єднання | blocked |
| портал зупинений після входу | дозвіл gateway завершується за таймаутом | blocked |

запит входу та звернення до ресурсу повинні надходити з одного симульованого пристрою. браузер хоста сам по собі не є `guest-client`. поява сторінки з назвою ролі без реального запиту через gateway не доводить застосування мережевого контролю.
