# Локальний Auth Portal і матриця доступу

Реалізація заняття 17 продовжує Sprint 2. Портал на Go `net/http` перевіряє пароль, зберігає користувачів і сесії у SQLite та видає тимчасові мережеві дозволи через gateway з nftables. Клієнт залишається у Guest; авторизація не змінює його підмережу.

## Запуск та тестові користувачі

```sh
python3 scripts/init-secrets.py
docker compose up -d --build --wait
python3 scripts/check-auth.py
```

Перший скрипт одноразово створює `.secrets/gateway-token` та `.secrets/test-users.json` з випадковими значеннями. Повторний запуск зберігає їх. Ці файли виключені з Git і Docker build context. Паролі тестових `student.test`, `teacher.test`, `admin.test` читаються локально з другого файлу. В SQLite зберігаються лише 16-байтові випадкові солі та PBKDF2-HMAC-SHA256 хеші з 600000 ітерацій. Зміна локального seed-файлу набуває чинності після перезапуску Portal; не використовуйте справжні паролі.

Портал доступний симульованим клієнтам за `http://172.28.10.20:8080`. Сторінку можна переглянути з хоста за `http://127.0.0.1:8080`, але мережевий login дозволений лише з реальних IP `guest-client` (`172.28.10.10`) та `guest-peer` (`172.28.10.11`). Браузер хоста не є Guest пристроєм. Скрипт retest виконує запити саме всередині контейнерів.

`GET /login` — HTML-форма, `POST /api/login` — поля `username`, `password`; роль береться з SQLite. `GET /api/me` повертає поточну роль. `POST /api/logout` відкликає дозвіл та видаляє сесію. API-клієнт передає `Accept: application/json`. Неправильні дані не створюють сесію чи дозвіл. Для одного IP діє одна активна ідентичність; повторний login спочатку відкликає попередні дозволи. Після 10 невдалих спроб за хвилину login для IP тимчасово обмежений.

## Ресурси та дозволи

Усі три ресурси обслуговує `internal-site` на `172.28.20.10`; окремі TCP-порти дозволяють gateway реально розрізняти ролі. Вміст ресурсів — навчальні тестові сторінки, не університетська інформаційна система.

| Роль | Інтернет TCP 80/443 | Матеріали TCP 80 | Сервіс викладача TCP 8081 | Адміністративний сервіс TCP 8082 |
| --- | --- | --- | --- | --- |
| Guest без входу | дозволено | заборонено | заборонено | заборонено |
| Student | дозволено | дозволено | заборонено | заборонено |
| Teacher | дозволено | дозволено | дозволено | заборонено |
| Admin | дозволено | дозволено | дозволено | дозволено |

Admin не має необмеженого мережевого доступу: дозволені лише ці три порти. IoT → Corporate блокується незалежно від активних ролей. Тимчасовий TCP/8080 у негативному тесті не є рольовим сервісом і має залишатися закритим навіть для Admin.

## Сесії та gateway

Токен сесії — 32 випадкові байти; SQLite зберігає SHA-256 токена, користувача, IP та час завершення. Cookie має `HttpOnly`, `SameSite=Strict`, обмежений термін і шлях `/`. Для локального HTTP `Secure=false`; у HTTPS-розгортанні задайте `COOKIE_SECURE=true`. Production TLS не входить до цієї лабораторної. `Origin` і `Sec-Fetch-Site` перевіряються на запитах зміни стану. `X-Forwarded-For` не використовується: IP береться з TCP-з'єднання.

Portal (`172.28.50.10`) і gateway (`172.28.50.254:9090`) мають окрему внутрішню Docker management-мережу `172.28.50.0/24`. Управління приймає лише автентифікований `POST /grant` з IP, роллю та TTL. Gateway перевіряє IP, роль і TTL; bearer-токен зберігається в локальному Docker secret. Input-правило gateway блокує TCP/9090 з Guest та IoT; запит із Portal без токена отримує 401.

Gateway атомарно замінює nftables-набір `role_access` з елементами `IP . TCP-port` і незалежним timeout для кожного дозволу. Час дозволу не перевищує час сесії; мережевий доступ може закінчитися менш ніж на секунду раніше через округлення TTL. Оновлення одного клієнта зберігає абсолютний термін іншого. Авторизація підтверджується лише після успішного застосування nftables. Якщо gateway відхиляє операцію, успішний login не повертається.

Дозволи Guest та загальна заборона Guest → Corporate стоять перед `established/related`; Logout та TTL блокують також подальші запити раніше встановленого TCP-з'єднання. Зупинка Portal не продовжує дозволи: kernel timeout gateway працює незалежно. Перезапуск gateway очищає набір; для відновлення доступу потрібен новий login, навіть якщо cookie ще чинна. Перевірка `/api/me` показує чинність сесії, а не факт наявності мережевого дозволу після restart gateway.

## Baseline та відтворюваність

Default TTL — 300 секунд; значення 5–3600 задається `SESSION_TTL_SECONDS`. Скрипт `scripts/check-auth.py` тимчасово встановлює 12 секунд, виконує retest і regression, а в `finally` повертає TTL 300 та очищає дозволи через recreation gateway. Він перезапускає і пересоздає контейнери, тому запускайте його без стороннього трафіку.

Кожен прогін створює окремий каталог `evidence/lab-17/<date_time>`; попередні докази не перезаписуються. До виконання записуються очікування, після — сценарні логи, загальний лог, результати та SHA-256 вихідних файлів. Паролі й cookie не виводяться в evidence; локальні шляхи та hostname замінюються нейтральними значеннями.

Перевірки включають неправильний пароль, повну матрицю портів, незалежність двох IP, копіювання cookie, зниження ролі, Logout встановленого з'єднання, TTL, зупинку Portal, недоступність management API, відмову застосування nftables і відновлення. Регресія повторює альтернативний порт, IoT-ізоляцію, Guest HTTP/HTTPS, restart gateway і recreation стенда.

Це trusted-client PoC: клієнти мають `NET_ADMIN` для маршрутів; захист від навмисного spoofing IP чи зміни маршрутів учасником не заявляється. Перевірки після readiness не доводять безперервної ізоляції під час recreation контейнерів. Перед інтеграцією на іншому середовищі повторіть перевірки.
