# Лабораторна робота з контролю доступу до університетської мережі

[English version](README.md)

Навчальний прототип (PoC) у Docker Compose для розділення гостьового, корпоративного та IoT-трафіку в університетській мережі. Локальний портал входу визначатиме користувачів, а Linux-шлюз застосовуватиме правила мережевого доступу.

Поточна основа спринту 2 додає Firewall на шлюзі до топології Docker Compose зі спринту 1. Запити Guest та IoT до Corporate блокуються; пересилання пакетів працює за принципом Default Deny. Портал, автентифікація, рольові дозволи та NAT для інтернету залишаються подальшою роботою. Збирання та перевірки ізоляції пройдено 26 жовтня 2026 року, зокрема після перезапуску шлюзу та пересоздання контейнерів. Див. [результати та фактичні логи](evidence/sprint-2/results.md).

## Запуск поточної мережевої моделі

За запущеного Docker та наявності Docker Compose виконайте з кореня репозиторію:

```bash
docker compose config --quiet
docker compose up -d --build --wait
sh scripts/check-isolation.sh
```

Скрипт перевіряє роботу Nginx, доступ шлюзу до сайту, доступ клієнтів до шлюзу та блокування запитів Guest/IoT до `172.28.20.10` зі зростанням відповідних лічильників Firewall. Очікувані таймаути запитів є частиною успішної перевірки ізоляції. Порт сайту на хості не опубліковано.

Перевірте збереження ізоляції після пересоздання контейнерів:

```bash
docker compose up -d --force-recreate --wait
sh scripts/check-isolation.sh
```

Шлюз стає готовим до роботи лише після завантаження правил nftables. Під час запуску Compose інші сервіси очікують успішного healthcheck шлюзу. Зміни конфігурації завантажуються після перезапуску; після змін Dockerfile або entrypoint потрібно перебудувати образ шлюзу.

Зупинка стенда: `docker compose down`. Політика Firewall, ручні перевірки й завдання учасникам наведені в [спринті 2](sprints/sprint-2-ua.md). [Спринт 1](sprints/sprint-1-ua.md) зберігає опис початкової моделі без обмежень та історичні результати її перевірки.

## Ідея проєкту

Клієнт починає роботу з гостьовим доступом: може відкрити портал входу та користуватися інтернетом, але не має доступу до внутрішніх сервісів університету. На порталі є поля логіна й пароля, кнопки **Увійти** та **Продовжити як гість**.

Після успішного входу портал показує роль користувача: **Student**, **Teacher** або **Admin**. У повній реалізації портал також просить шлюз надати цьому клієнту мережеві дозволи відповідно до ролі. Вихід з облікового запису або завершення терміну дії сесії скасовує ці дозволи.

Guest — початковий стан без автентифікації. Student, Teacher та Admin — ролі автентифікованих користувачів. Guest, Corporate та IoT — мережеві сегменти; ролі й сегменти є окремими поняттями. Вхід не переміщує клієнта до іншої Docker-мережі.

## Обраний технологічний стек

Запланований бекенд порталу використовуватиме Go зі стандартним пакетом `net/http` для обробки HTTP-запитів, перевірки облікових даних, роботи із сесіями, визначення ролей та подальшої інтеграції зі шлюзом. Фронтенд використовуватиме звичайні HTML, CSS і JavaScript для `/login` та сторінки ролі, без фронтенд-фреймворку. SQLite зберігатиме тестові облікові записи, хеші паролів і сесії.

Go-застосунок віддаватиме файли фронтенда та API з одного контейнера `portal`. Маршрутизація та застосування правил міжмережевого екрана залишатимуться в окремому Linux-контейнері шлюзу. Цей стек обрано для подальшої реалізації; портал ще не входить до поточної робочої моделі.

## Компоненти

| Компонент | Призначення |
| --- | --- |
| Клієнт | Docker-контейнер, що представляє пристрій користувача. Надсилає запити входу та намагається звертатися до мережевих ресурсів. |
| Фронтенд порталу | Інтерфейс на JavaScript за адресою `/login` і сторінка з поточною роллю після входу. |
| Бекенд порталу | Перевіряє облікові дані, створює сесії, пов'язує IP клієнта з користувачем і роллю та запитує зміну дозволів на шлюзі. |
| База даних SQLite | Зберігає тестові облікові записи, хеші паролів, ролі та активні сесії. Паролі у відкритому вигляді не зберігаються. |
| Шлюз / міжмережевий екран | Linux-контейнер, що маршрутизує трафік між сегментами та застосовує правила; використовується `nftables`. |
| Внутрішній ресурс | Окремий сайт університету в Corporate. Для демонстрації мережевого контролю доступу достатньо статичної сторінки Nginx; окремий бекенд застосунку необов'язковий. |
| IoT-клієнт | Контейнер для перевірки ізоляції IoT-пристроїв від сервісів Corporate. |

## Схема мережі

```text
Мережа Guest                         Мережа Corporate
  Клієнт ------ Шлюз / Firewall ------ Внутрішній ресурс
  Портал входу         |
                       +------ IoT-клієнт (мережа IoT)
                       |
                       +------ Вихід в інтернет
```

Портал має бути доступним до автентифікації. Трафік від клієнтів до внутрішніх ресурсів має проходити через шлюз. Контейнери клієнтів і ресурсів не повинні мати спільної альтернативної мережі для обходу шлюзу. Під час перевірки гостьового доступу до інтернету відповідний трафік також має проходити через шлюз.

Docker Compose призначає клієнтам стенда фіксовані IP-адреси. Поточні підмережі, адреси та маршрути наведено в описі [спринту 1](sprints/sprint-1-ua.md). Шлюз має можливість `NET_ADMIN` та пересилання IPv4-пакетів, увімкнене через Docker Compose. Вихід в інтернет і NAT ще потрібно налаштувати й перевірити.

Це віртуальна модель мережі. Фізична точка доступу Wi-Fi не потрібна. Користувачі відкривають портал самостійно; автоматичне виявлення captive portal і перенаправлення не входять до початкового задуму.

## Послідовність входу та надання мережевого доступу

1. Клієнт починає роботу в Guest із доступом до порталу та інтернету. Шлюз блокує внутрішні сервіси.
2. Клієнт відкриває `/login`. Вибір **Продовжити як гість** зберігає поточні гостьові дозволи.
3. Користувач надсилає облікові дані. Бекенд перевіряє хеш пароля та отримує роль облікового запису з SQLite. Користувач не може вибрати або підмінити роль у запиті.
4. Бекенд записує сесію: користувача, роль, IP клієнта та час завершення дії.
5. Через обмежений інтерфейс керування бекенд просить шлюз застосувати мережеві дозволи ролі до цього IP. Клієнти не мають доступу до цього інтерфейсу.
6. Портал показує роль. Подальші запити до внутрішніх ресурсів дозволяються або блокуються правилами міжмережевого екрана на шлюзі.
7. Вихід або завершення сесії скасовує дозволи на шлюзі та повертає клієнту гостьовий доступ. Активні дозволи також мають втрачати чинність на шлюзі, якщо портал припинить працювати.

Шлюз не перевіряє паролі або сторінку з роллю. Він зіставляє адреси джерела, адреси призначення та порти пакетів із установленими правилами. Портал перетворює роль автентифікованого користувача на ці правила.

## Де зберігається інформація

| Інформація | Місце зберігання |
| --- | --- |
| Фіксований IP клієнта та належність до мережі | Конфігурація Docker Compose |
| Логін, хеш пароля та роль | База даних SQLite порталу |
| Зв'язок користувача з IP та час завершення сесії | Записи сесій порталу |
| Активні мережеві дозволи для IP | Правила або набори міжмережевого екрана шлюзу |

Портал має отримувати справжній IP клієнта зі з'єднання. Перш ніж увімкнути дозволи за IP, потрібно врахувати проксі або Docker NAT на цьому шляху.

У цій лабораторній кожен змодельований пристрій має окремий фіксований IP та одну активну ідентичність одночасно. Дозвіл за IP поширюється на весь пристрій, зокрема на інші його браузерні сесії. Ця спрощена модель не охоплює підміну IP, клієнтів зі спільним NAT або керування мережевими ідентичностями у виробничому середовищі.

## Ролі та дозволи

Початкова демонстрація ролей може показувати після входу **Твоя роль: Student**, **Твоя роль: Teacher** або **Твоя роль: Admin**. Це перевіряє автентифікацію та призначення ролі, але саме по собі не демонструє застосування мережевих обмежень.

Мінімальна мережева демонстрація розрізняє гостя й автентифікованого клієнта: той самий внутрішній ресурс недоступний до входу та доступний після нього. Для демонстрації різних мережевих дозволів Student, Teacher та Admin потрібна погоджена матриця ресурсів і портів. Її ще потрібно визначити; самі назви ролей не задають правил міжмережевого екрана.

Ізоляція IoT від Corporate — окрема мережева політика, яка не залежить від входу користувача.

## Як перевірятиметься повна модель

Запити входу та звернення до ресурсів мають надходити від того самого змодельованого клієнта, щоб шлюз перевіряв IP, якому надано дозвіл. Браузер на хості дозволяє переглянути портал, але автоматично не представляє клієнта в Docker.

| Сценарій | Очікуваний результат |
| --- | --- |
| Guest звертається до порталу | Портал доступний. |
| Guest звертається до інтернету | Запит успішно проходить через шлюз. |
| Guest звертається до внутрішнього ресурсу | Шлюз блокує з'єднання. |
| Вхід кожним тестовим обліковим записом | Портал показує роль, збережену для цього облікового запису. |
| Надіслано неправильні облікові дані | Вхід відхилено, мережевий дозвіл не створюється. |
| Автентифікований клієнт звертається до дозволеного внутрішнього ресурсу | З'єднання успішне. |
| Інший клієнт залишається без автентифікації | Його доступ залишається заблокованим. |
| Клієнт виходить або сесія завершується | Внутрішній доступ знову блокується. |
| IoT-клієнт звертається до Corporate | Шлюз блокує з'єднання згідно з політикою ізоляції. |

Застосування мережевих обмежень перевірятиметься реальними запитами, наприклад `curl` із клієнтських контейнерів, разом із лічильниками або журналами міжмережевого екрана. Сама HTTP-помилка від порталу не доводить, що мережа блокує прямий доступ до ресурсу. Перевірки скасування дозволів мають також охоплювати вже встановлені з'єднання, якщо міжмережевий екран дозволяє такий трафік.

Докази включатимуть команду або дію, очікуваний результат, фактичний результат, статус PASS/FAIL і журнали або знімки екрана, що його підтверджують.
